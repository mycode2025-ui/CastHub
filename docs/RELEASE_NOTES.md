检查更新现在**优先走 Gitee**，不再动不动就查不到新版本。

## 为什么要改

GitHub 的未登录接口是「每出口 IP 每小时 60 次」，而应用内检查更新不能内置令牌、
只能走未登录接口。国内共享出口 IP 上这个额度经常是 0 —— 实测表现为检查更新直接失败，
明明有新版本却提示「检查更新失败」。

改完后：Gitee 取到版本就用 Gitee，GitHub 被限流也只是多一条告警，结论照常给出。

实测同一时刻的日志：

```
Gitee  取到 1 条 Release          ✅
GitHub 取版本失败：访问受限（每小时仅 60 次）
结论：发现新版本（版本信息来自 Gitee）
```

换成以前的写法，这一刻会直接报「检查更新失败」。

## 不是"只查 Gitee"

两站的发布节奏并不一致，只查一个会漏判。所以两站**都查**、取版本更高的那个，
「优先 Gitee」只在**版本相同时**决定版本信息和安装包取自哪个站 ——
不会因为优先 Gitee 就无视 GitHub 上更高的版本。

界面上会写明「版本信息来自 Gitee / GitHub」，两站结果不一致时也会说明原因。

## 另外两处

· **下载失败可以换源重试**：同一个版本在另一站也挂着安装包时，失败提示里直接给
  「改用 Gitee / GitHub 重试」按钮，而不是只留一个发布页链接让用户自己找。
  （只提示、不自动重试 —— 几 MB 的包下到一半自动重来一遍，在电视上像卡死。）
· **授权后自动继续**：以前「去设置」打开「安装未知应用」再返回，升级流程就断了，
  得重新点一次「立即升级」（还得多查一次更新）。现在回来会自动接着走。

## 关于这个版本号

1.4.1 的安装包**已经包含**本次改动，但源码当时没提交、tag 仍指向改动前的提交 ——
tag 与代码不一致。所以发 1.4.2 把 tag 追上代码，两边重新对齐。

如果你已经装了 1.4.1，功能与 1.4.2 相同，升不升级都行。

`minSdk 23`（Android 6.0），`targetSdk 34`。签名与 1.4.0 / 1.4.1 一致，可直接覆盖升级。
